Signal · Design round 3 · Prototype 4b · Compare direction

Need → decide → publish

A PM opens the most-wanted need, reads every signal, corrects one AI score, has AI draft a decision brief, edits it, and publishes a status and a note. Every supporter sees that note on their own private page.

Steps
  1. Needs: open the top need (seed n1, executives sharing dashboard snapshots).
  2. Need detail: statement, public summary, proposed solutions, all 11 signals word for word with person, account, plan, ARR, use case and urgency, accounts, and merge history.
  3. Priority: the AI's per-criterion scores are in pencil until the PM resolves them. The PM overrides Effort 3 → 2 and adds a note. The suggestion resolves, turns to ink, and the score goes from 4.2 to 4.1.
  4. Draft decision brief: a short loading line, then a pencil brief covering demand, accounts and value, options, and a recommendation.
  5. Edit the brief's markdown, then Accept with edits. It turns to ink and shows "edited by you".
  6. Decide: pick a status (Planned / In progress / Shipped / Declined) and write the public note. Both are prefilled from the brief in pencil, and a client-side check looks for names and revenue.
  7. Publish. The confirmation previews one supporter's My signals page, with Lynda's three signals grouped on one private page.
API
get_need_detail → resolve_suggestion (priority, edit: {scores:{effort:2}, reasons:{effort}}) → draft_decision_brief (a pending decision_brief suggestion) → resolve_suggestion (edit: {markdown}) → publish_decision {id, status, note} → get_my_signals. The Triage count in the top bar follows the pending suggestions. The line above the frame names each call as it happens.
Not in API
(1) Grouping one person's signals on one My signals page. get_my_signals reads one tracking token, and tokens are issued per submission, so today Lynda would have three separate links. (2) Previewing a supporter's page from the console. The Operator has no way to read My signals by person, so the preview is assembled from get_need_detail and public data. (3) The "no names, people, revenue" check on the note is client-side only. publish_decision asks for this in its description but does not enforce it. (4) Overriding a score after the priority suggestion is resolved is not offered, because it would need a new priority suggestion and no operation creates one on demand.
Seed data
All 11 signals, people, accounts, ARR, open deals, use cases, urgency, dates, the public summary, the proposed solutions, the rejected n2 → n1 merge, and Lynda Skiles's other two signals come from seedDemoWorkspace, run with seed 20261030 and today's date (Oct 30). The Needs table uses seed numbers, so it does not match round 2: n1 has 8 accounts and $1.38M ARR, not 4 and $1.07M.
Invented
The seed has no scores for n1, so its pending AI priority suggestion is invented: Demand 5, Business value 4, Fit 4, Effort 3, with reasons, giving 4.2 under the seeded weights. The PM's override note and brief edit are also invented. The brief's AI prose (summary, option rationales, recommended note) is invented, but its facts lines are derived from the seed. The seed has no accepted merge into n1, so Undo merge is not exercised here. Only the rejected merge suggestion appears, and accepted merges would get an Undo control in the same list. If 4a's triage merge targets n1, that row and its Undo belong here.
Risks
Eleven quotes make a long page. That is intentional, because the PM should read them, but a need with 60 signals will need grouping by ask. Prefilling the note from the brief invites publishing AI words unread; the pencil marking until the note is touched is the only guard. On phone the brief's markdown editor is usable, but it is not pleasant to use.
